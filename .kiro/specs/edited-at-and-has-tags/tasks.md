# Implementation Plan

各タスクの完了時点で、既存テストを含めて全テストが通る状態を保つ。タスクごとにコミットする。

- [ ] 1. 本体テーブルへの列追加と既存データのコピー
- [x] 1.1 編集日時とタグの有無の列を、本体テーブルに追加する
  - メモ・ブックマークに編集日時（null 可）とタグの有無（既定は「なし」）を、タグに編集日時（null 可）を追加する
  - ロールバックでは、追加した列だけを削除する
  - この時点では、アプリは引き続き status テーブルのタグの有無を使う
  - _Requirements: 1.1, 5.1, 10.1_
- [ ] 1.2 既存データの編集日時とタグの有無を、本体テーブルへ写す
  - ゴミ箱内を含むすべてのメモ・ブックマークと、すべてのタグの編集日時に、行の更新日時を写す
  - status テーブルのタグの有無を、メモ・ブックマークの本体へ写す。status 行が無い本体は「なし」のままにする
  - 移行の過程で、行の更新日時を変えない
  - ロールバックでは、本体のタグの有無を status テーブルへ書き戻す
  - 移行のテストを追加する（ゴミ箱内の行、status 行が無い本体、行の更新日時が変わらないこと、ロールバックでの書き戻し）
  - _Requirements: 7.1, 7.2, 7.3, 7.4, 10.9_
- [ ] 1.3 既存のマイグレーションテストを、新しい列が増えた状態でも動くように直す
  - 古いマイグレーションの取り消しを検証する既存テスト2本は、準備処理で今回のマイグレーションを新しい順に取り消してから、従来の取り消しを行う形にする
  - テストは削除せず、検証内容も変えない
  - _Requirements: 7.4_

- [ ] 2. 編集日時の自動設定
- [ ] 2.1 作成時と編集時に、編集日時を自動で設定する仕組みを作る
  - 作成時は、編集日時を作成日時と同じ時刻にする。呼び出し側が編集日時を明示した場合は、その値を使う
  - 編集対象の属性が変わった保存では、編集日時を行の更新日時と同じ時刻にする
  - 本体の属性が変わらない編集を、次の保存で編集として扱う手段を用意する（モデルを変更ありの状態にし、保存後に印を消す）
  - 変更の無い保存では何も書かない
  - _Requirements: 1.2, 1.3, 1.5, 10.2_
- [ ] 2.2 メモ・ブックマーク・タグに、編集日時の自動設定を適用する
  - 編集対象の属性は、メモがタイトル・本文・星、ブックマークがタイトル・URL・星、タグが名前
  - 編集日時を日時として扱い、モデルの型情報（プロパティの注釈）に追加する
  - テスト：作成時に作成日時と一致する、編集対象の変更で更新される、変更なしでは変わらない、ゴミ箱への移動・復元では変わらない、変更ありの印だけで更新される、タグ名の変更で更新され同じ名前では変わらない、タグの使用回数の増減では変わらない
  - _Requirements: 1.1, 1.2, 1.3, 1.5, 2.4, 10.1, 10.2, 10.3, 10.4, 10.5_

- [ ] 3. 並べ替え・絞り込み・レスポンス・排他制御を、編集日時に切り替える
- [ ] 3.1 楽観的排他制御とタグの付け替えを、編集日時に切り替える
  - 「取得後に更新されたか」の判定を、編集日時との比較に変え、意味に合わせて名前も変える（メモの取得・更新の2か所）
  - タグだけを付け替えた更新は、行の更新日時を直接更新する代わりに、編集として印を付けてから保存する
  - テスト：取得日時より後に編集されていれば競合になる、タグだけの付け替えで編集日時が更新される、内容が同じなら更新されない
  - 既存テストのうち、行の更新日時を指定して競合を作っている箇所は、編集日時を指定する形に直す
  - _Requirements: 1.4, 1.5, 4.1, 4.3_
- [ ] 3.2 メモ検索の並べ替え・期間絞り込み・レスポンスを、編集日時に改名する
  - 並べ替えの既定値と許可値を編集日時に変え、旧名の並べ替えは受け付けない
  - 期間指定のパラメータを編集日時の名前に変え、旧名のパラメータはバリデーションエラーにする
  - メモのレスポンスでは、行の更新日時の代わりに編集日時を返す
  - テスト：編集日時順の並び（既定を含む）、期間での絞り込み、旧名のパラメータで 422、レスポンスに編集日時があり行の更新日時が無いこと
  - 既存テストのうち、行の更新日時を指定して並び順・期間を作っている箇所は、編集日時を指定する形に直す
  - _Requirements: 3.1, 3.2, 3.3, 3.4_
- [ ] 3.3 (P) タグ検索の並べ替えとタグのレスポンスを、編集日時に改名する
  - タグ検索の並べ替えの既定値と許可値を編集日時に変え、旧名の並べ替えは受け付けない
  - タグのレスポンスでは、行の更新日時の代わりに編集日時を返す（タグ検索・全タグ取得・メモのレスポンス内のタグ）
  - テスト：編集日時順の並び（既定を含む）、旧名の並べ替えで 422、レスポンスに編集日時があり行の更新日時が無いこと
  - 3.2 とは別の検索・レスポンスを変更するため並行できる。ただし、メモのレスポンスに含まれるタグの検証は 3.2 のテストと重なるので、マージ時に確認する
  - _Requirements: 10.6, 10.7, 10.8_
- [ ] 3.4 フロントエンド用の生成ファイルを再生成する
  - ルート定義と API スキーマを再生成し、メモ・タグの型が編集日時になっていることを確認する
  - フロントエンドの型チェックが通ることを確認する
  - 3.2 と 3.3 の完了後に行う
  - _Requirements: 3.5_

- [ ] 4. タグの有無の管理を本体テーブルへ切り替える
- [ ] 4.1 紐付けの増減に合わせた同期の書き込み先を、本体テーブルへ切り替える
  - 1つ目のタグが紐付いたら「あり」、最後のタグが外れたら「なし」にする書き込み先を、status 行から本体（ゴミ箱内を含む）に変える
  - 行の更新日時は通常どおり更新し、編集日時は変えない
  - メモ・ブックマーク・タグの本体で、タグの有無の既定値と型を扱えるようにする
  - テスト：追加・解除・付け替えで本体のタグの有無が変わる、行の更新日時が更新され編集日時は変わらない、ゴミ箱内も対象になる
  - _Requirements: 1.6, 5.1, 5.3, 5.4, 5.6_
- [ ] 4.2 タグ削除時の同期を、本体テーブルへ切り替える
  - 削除するタグ以外に紐付いていないメモ・ブックマーク（ゴミ箱内を含む）の、本体のタグの有無を「なし」にする
  - テスト：本体のタグの有無が「なし」になる、編集日時は変わらない、タグ削除の後に更新しても競合にならない、タグ削除で編集日時順の並びが変わらない、タグ名の変更でメモの編集日時が変わらない
  - _Requirements: 1.6, 2.1, 2.2, 2.5, 4.2, 5.5, 5.6_
- [ ] 4.3 タグなし検索を、本体のタグの有無で絞り込む形に切り替える
  - 検索したユーザーの、本体のタグの有無が「なし」のメモだけを返す
  - テスト：他ユーザーのメモを含まない、ゴミ箱検索と組み合わせられる
  - 4.1 の完了後に行う（本体のタグの有無が同期されている前提）
  - _Requirements: 6.1, 6.2, 6.3_
- [ ] 4.4 status 行のモデルから、タグの有無の扱いを取り除く
  - メモ・ブックマークの status 行は、閲覧数だけを扱う。タグの有無のための中間の基底を廃止し、タグの status 行と同じ形にする
  - status 行と、その作成を担う仕組みの説明を、閲覧数・使用回数だけを扱う内容に更新する
  - 閲覧数の加算で、メモの編集日時と行の更新日時が変わらないことをテストする
  - _Requirements: 2.3, 5.2, 5.7_

- [ ] 5. スキーマの仕上げ（NOT NULL 化・インデックス・status からの削除）
- [ ] 5.1 編集日時の NOT NULL 化、インデックスの作り直し、status テーブルからのタグの有無の削除を行う
  - メモ・ブックマーク・タグの編集日時を NOT NULL にする
  - メモ・ブックマークに、通常一覧用（ユーザー・論理削除・編集日時）とタグなし検索用（ユーザー・タグの有無・論理削除・編集日時）の複合インデックスを作ってから、行の更新日時を使う旧インデックスを削除する（外部キー用のインデックスを途切れさせない）
  - status テーブルから、タグの有無の列を削除する
  - ロールバックでは、status テーブルの列と旧インデックスを戻し、新しいインデックスを削除し、編集日時を null 可に戻す
  - _Requirements: 5.1, 5.7, 6.4, 6.5, 7.2, 7.4_
- [ ] 5.2 移行全体の往復を検証する
  - テスト：3段階のマイグレーションを新しい順に取り消すと、移行前の構造と値に戻る
  - テスト：移行前と同じデータに対して、編集日時順の並び順とタグなし検索の結果が移行前と変わらない
  - 1.3 で直した既存のマイグレーションテストが、今回の3段階すべてを取り消してから動くことを確認する
  - 開発 DB（MariaDB）で、マイグレーションの実行・取り消し・再実行を確認する
  - _Requirements: 7.4, 7.5_

- [ ] 6. 旧データ移行コマンドを新しい構造に合わせる
  - メモ・ブックマークの取り込みで、編集日時に旧データの更新日時を設定し、タグの有無を本体に設定する（判定方法は変えない）
  - status テーブルへの取り込みは、閲覧数・使用回数だけにする
  - タグの取り込みで、編集日時に旧データの更新日時を設定する
  - 静的解析が通ることを確認する
  - _Requirements: 8.1, 8.2, 10.10_

- [ ] 7. タグなし検索の性能を計測する
  - 開発 DB で、1ユーザー20,000件（他ユーザーを含め全10万件、本文約1KB）を用意し、タグなし件数（3件・1%・10%・50%・90%）ごとに、アプリが発行する SQL の1ページ目と件数取得を計測する
  - どのケースも20ms以下であること、DB のセッション変数を設定していないことを確認する
  - 実行計画で、タグなし検索用の複合インデックスが使われ、並べ替えのための一時処理（filesort）が出ないことを確認する
  - 計測用のデータは計測後に削除する
  - _Requirements: 6.4, 6.5_

- [ ] 8. 定義ドキュメントと調査記録を更新する
  - メモ・ブックマーク・タグ・各 status テーブルの DB 定義に、行の更新日時と編集日時の違い、タグの有無の格納先、インデックス、7 の計測結果を記載する
  - status テーブルの分離理由を、閲覧数・使用回数だけを対象とする内容にする
  - モデル定義とメモ・タグの API 定義に、並べ替え・期間絞り込み・レスポンス・排他制御が編集日時に基づくこと、タグの有無の同期先を記載する
  - `.research-docs` の has_tags に関する記録を、新しい格納先と同期方法に合わせて更新する
  - _Requirements: 9.1, 9.2, 9.3, 9.4_
