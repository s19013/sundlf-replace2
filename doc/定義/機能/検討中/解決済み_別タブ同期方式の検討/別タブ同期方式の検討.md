## 前提・課題

同じメモを複数タブで開いている場合に、一方のタブが古い状態のまま表示され続けることがある(原因不明、キャッシュの可能性)。
常に最新の状態にしたいが、**ユーザーが未保存で編集中のデータを勝手に上書きされたくない**という制約もある。

「別タブの内容が変わったことをどう検知し、いつ再取得するか」という更新検知方式と、「取得した内容と未保存の編集内容が競合したときにどうするか」という競合解決方式は分けて考える必要がある。本ドキュメントは主に前者(更新検知方式)を扱う。

## 更新検知方式の選択肢

### 1. ポーリング(Polling)

一定間隔(例: 10〜30秒ごと)で `setInterval` によりメモ取得apiを呼び出し、サーバー側の `updated_at` 等と比較して変化があれば画面に反映する。

- **メリット**
  - 実装が単純。どのブラウザ・環境でも確実に動く。
  - 別タブに限らず、別デバイス・別ユーザーによる更新(将来共有機能を追加した場合等)にも同じ仕組みで対応できる。
- **デメリット**
  - タブを開いている間ずっと定期通信が発生し、サーバー負荷・通信量が増える。
  - 間隔を短くすると負荷増、長くすると「最新化まで時間がかかる」というトレードオフが常につきまとう。
  - タブが非アクティブでも通信し続けるため無駄が多い(ブラウザによっては非アクティブタブのタイマーが間引かれる場合もあり、挙動が読みにくい)。

### 2. フォーカス/visibility時再取得

タブ・ウィンドウにフォーカスが戻った瞬間(`window` の `focus` イベント、または `document.visibilitychange` で `visible` になった瞬間)にメモ取得apiを1回呼び出す。

- **メリット**
  - 実装が単純(イベントリスナー1つ)。追加の定期通信が発生しない。
  - 「ユーザーがそのタブを見ようとした瞬間に最新化する」という体験として自然。
- **デメリット**
  - タブを切り替えずに長時間同じタブだけを見ている場合は更新に気づけない(ただしその間は自分でそのタブを編集しているはずなので実害は小さい)。
  - フォーカスの当たらない裏タブ同士の同期はできない(あくまで「見に来たときに最新化する」方式)。

### 3. BroadcastChannel API

同一オリジンのタブ間で直接メッセージを送受信できるブラウザ標準API。あるタブでメモを更新したら、`BroadcastChannel` 経由で他タブへ「このメモが更新された」というメッセージを即座にpush通知し、受け取ったタブが再取得または差分反映する。

- **メリット**
  - サーバーへの追加通信なしで、他タブに**即時**に変化を伝えられる(pushなのでポーリングの遅延がない)。
  - 「自分の別タブでの更新」という今回のユースケースに対して最も的確(サーバーを介さずブラウザ内で完結)。
- **デメリット**
  - 同一ブラウザ・同一オリジンのタブ間でしか使えない(別ブラウザや別デバイスでの更新は検知不可)。
  - Safari は比較的新しいバージョンでの対応(iOS Safari 15.4+ 等)のため、対象ブラウザによっては要確認。
  - タブを閉じた後に開いた別タブなど、「今開いていないタブ」への通知はできない(その場合は初期表示時の取得で担保される)。

### 4. localStorage の `storage` イベント

あるタブで `localStorage` に「更新があった」という値(例: メモID+タイムスタンプ)を書き込むと、**他の**タブ(書き込んだ本人のタブ以外)で `storage` イベントが発火する。これを購読して再取得のトリガーにする。

- **メリット**
  - BroadcastChannel より対応ブラウザが広い(古いブラウザでも動く)、実装もシンプル。
- **デメリット**
  - 「他タブ間の伝言板」としての用途に localStorage を流用する形になり、本来の用途(永続ストレージ)からは少し外れる。書き込むキーの設計・後片付けを自前で管理する必要がある。
  - BroadcastChannel が使えるなら基本的にそちらの方が素直(こちらは主にBroadcastChannel未対応環境へのフォールバックという位置づけ)。

### 5. WebSocket / Server-Sent Events(SSE)によるサーバーpush

サーバー側でメモが更新されたタイミングで、WebSocketやSSEを使ってクライアントにpush通知する。

- **メリット**
  - 別タブに限らず、別デバイス・別ブラウザからの更新も含めて即時に検知できる。将来的な共同編集・他デバイス同期まで見据えるなら最も汎用的。
- **デメリット**
  - バックエンドに常時接続の仕組み(WebSocketサーバー、Laravel であれば Reverb/Pusher 等)を新設する必要があり、実装・運用コストが大きい。
  - 「本人が自分のメモを編集するだけ」という現状のスコープ(公開機能・共有機能は対象外)に対しては明らかにオーバースペック。

## 比較表

| 方式                         | 検知範囲                   | 即時性       | 追加通信/負荷          | 実装コスト |
| ---------------------------- | -------------------------- | ------------ | ---------------------- | ---------- |
| ポーリング                   | 同一データを見る全員       | 間隔依存     | 常時(高)               | 低         |
| フォーカス時再取得           | 自分の別タブ               | フォーカス時 | フォーカス時のみ(低)   | 低         |
| BroadcastChannel             | 自分の別タブ(同一ブラウザ) | 即時         | なし                   | 中         |
| localStorage storageイベント | 自分の別タブ(同一ブラウザ) | 即時         | なし                   | 中         |
| WebSocket / SSE              | 全デバイス・全ユーザー     | 即時         | 常時接続(サーバー側高) | 高         |

## 推奨

**フォーカス時再取得 + BroadcastChannel の組み合わせ**を推奨する。

- 今回の課題は「同一ユーザーが同一ブラウザで複数タブを開いている」というスコープであり、別デバイス・別ユーザー間の同期(将来の共有機能等)は [メモ/概要.md](../../メモ/概要.md) で対象外と明記されている。そのため、サーバー常時接続が必要な WebSocket/SSE は現時点では過剰。
- ポーリングは実装は楽だが、常時通信のコストに見合うほどの即時性・汎用性がこのユースケースでは不要。
- BroadcastChannel は「タブAで保存した瞬間にタブBへ即time通知」ができ、フォーカス時再取得は「BroadcastChannelが使えない/届かなかった場合(タブを閉じていた・対象ブラウザが未対応)」の保険として機能する。両者を組み合わせることで、追加の定期通信なしに実用上十分な即時性を確保できる。
- BroadcastChannel未対応ブラウザへの配慮が必要になった場合は、localStorageのstorageイベントをフォールバックとして追加する(対応コストは小さい)。

## 未保存データの上書き防止(競合解決)との関係

更新検知方式とは別に、「再取得した内容で今の未保存の編集内容を上書きしない」ための仕組みが必要。

- 再取得のタイミングでは即座に画面を上書きせず、「他のタブで更新されました。反映しますか?」等の確認を挟む、または未編集(フォームに変更がない)ときのみ自動反映する、といった制御を検討する。
- サーバー側の `updated_at` をもとに、保存時に「自分が取得した時点より新しい更新がある場合はエラーにする」楽観的排他制御(optimistic locking)を導入すると、検知方式に関わらず上書き事故を防げる。これは [機能/メモ/更新.md](../../メモ/更新.md) 側の仕様として別途検討が必要。

# 結論

## フォーカス時再取得のみを使う

BroadcastChannelをつかって他のタブへ｢即時｣伝える必要は薄いと思う。

フォーカス時再取得だけで十分だと思う。

## フォーカス時再取得

- フォーカス時、未編集(フォームに変更がない)ときのみ自動反映する
- 編集済みの場合、「他のタブで更新されました。反映しますか?」とモーダルを出す。
  - このモーダルに同意した場合、タイトル、紐付けているタグ、本文すべてを上書きする
  - 非同意した場合、モーダルは一旦閉じる、そして、ユーザーが保存した時、エラーを返して、本文入力フォームをgit conflictのような表示にする
    - [参考](./chatgpt_参考資料.md)

## 追加対応

### 取得時

`updated_at`も取得し、メモリに保管しておく

### 更新時

メモリに保存しておいた`updated_at`もサーバーへ送信

#### 同期ズレ判別処理

データベースの`updated_at`と送られてきた`updated_at`が同じか確かめる

サーバー側の `updated_at` をもとに、保存時に「自分が取得した時点より新しい更新がある場合はエラーにする」楽観的排他制御(optimistic locking)を導入する
