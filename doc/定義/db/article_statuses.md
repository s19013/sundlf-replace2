# カラム

| カラム名   | ラベル         | 型                  | nullable | デフォルト値 | インデックス | 備考                                                    |
| ---------- | -------------- | ------------------- | -------- | ------------ | ------------ | ------------------------------------------------------- |
| article_id | メモID         | bigint(20) UNSIGNED | false    |              | true         | 主キー、外部キー（`articles.id`）                       |
| user_id    | ユーザーID     | bigint(20) UNSIGNED | false    |              | true         | `articles.user_id` の写し。タグなし検索の絞り込みに使う |
| has_tags   | タグもちフラグ | bool                | false    | false        | true         | タグを紐付けているかどうかを管理                        |
| count      | 閲覧数         | bigint(20) UNSIGNED | false    | 0            | false        | 閲覧数増加APIで加算される（`メモ閲覧数増加api.md`参照） |
| created_at | 作成日時       | timestamp           | true     | NULL         | false        |                                                         |

メモ（[`articles.md`](./articles.md)）のうち、ユーザーが直接変更しない項目を管理するテーブル。

# リレーション

## article_id

`articles.id` を参照する外部キー。1つのメモに対して1行だけ存在する（1対1）。

## user_id

`articles.user_id` と同じ値を持つ。本体の写しなので外部キー制約は張らない。ユーザーが削除されたときは、`articles` の CASCADE 経由でこのテーブルの行も削除される。
メモの所有者は作成後に変わらないため、作成時に設定した後は更新しない。

# 制約

## article_id

主キー制約。1つのメモに対して status の行が複数作られないようにする。

外部キー制約（`article_statuses_article_id_foreign`）。`ON DELETE CASCADE` のため、参照先のメモが削除されると、このテーブルの行も削除される。

# インデックス

| 名前                                      | カラム                | 用途                                                   |
| ----------------------------------------- | --------------------- | ------------------------------------------------------ |
| `article_statuses_user_id_has_tags_index` | `(user_id, has_tags)` | タグなし検索で、ユーザーのタグなしの行だけを直接引く |

`article_id` は含めない。InnoDB はセカンダリインデックスの末尾に主キーを持つため。

# 備考

## 分離した理由

- `articles` にはユーザーが直接変更できる項目だけを置き、`count` / `has_tags` のようにサーバーが自動で更新する項目はこのテーブルで管理する。
- これらはメモの更新日時とは関係のない属性である。同じテーブルに置くと、更新日時を変えずに書き換える特別扱い（`withoutTimestamps`）が必要になり、検索の更新日順ソートや楽観的排他制御（`fetched_at`との比較）に影響しやすい。そのため別テーブルに分けた。
- 関連 issue: #118、#122、#127

## 行の作成・削除

- メモ作成時に、同じトランザクション内でこのテーブルの行も作成する。`user_id` には本体の値を設定する（`Entry::statusRowAttributes()`）。
- 論理削除（ゴミ箱）中も行は残す。メモが物理削除されたときに CASCADE で削除される。

## 既存データの移行

移行時に、`articles` の `count` / `has_tags` の値を使って全メモ分の行を作成する。その後、`articles` から両カラムを削除する。

`user_id` は後から追加した（#131）。nullable で追加し、`articles.user_id` をゴミ箱内も含めてコピーしてから、NOT NULL にしてインデックスを作成する。

## 行が無い場合の扱い

行は作成時のイベントと移行で必ず作られる前提で、欠けた場合の対応はしない。欠けるのは、イベントを通さずに作られたメモなどに限られる。

- タグなし検索は「`has_tags = false` の行がある」で絞り込むため、行が無いメモはタグなし検索に出ない（#131 で変更。以前はタグなしとして扱っていた）。
- 閲覧数の加算や `has_tags` の同期は UPDATE だけなので、行が無いと反映されない（自動では補わない）。

## 検索への影響

タグなし検索は、このテーブルの `(user_id, has_tags)` インデックスでユーザーのタグなしの行を引き、`articles.id IN (...)` で絞り込む。

以前は「`has_tags = true` の行が無い」で判定していたが、全ユーザー分の行を毎回一時テーブルに読み込む実行計画になり、ユーザー数に比例して遅くなっていた（#131）。

タグなしが多いユーザーでは、オプティマイザがこのテーブルを起点に全件を並べ替える計画を選び、1ページ目が遅くなる。そのため、アプリの DB 接続で MariaDB の `optimizer_join_limit_pref_ratio` を 100 に設定している（`config/database.php`）。`ORDER BY ... LIMIT` のときに、`articles` を更新日時順に読んで途中で止まる計画も比較させる設定で、MariaDB 10.6.17 / 10.11.7 / 11.0.5 以降で使える。値は環境変数 `DB_OPTIMIZER_JOIN_LIMIT_PREF_RATIO`（既定100）で変えられ、この変数が無いDB（MySQL本体・古いMariaDB）では空にして送らないようにする（送ると接続時にエラーになる）。

開発環境（MariaDB 12.0）で、1ユーザー20,000件（本文約1KB、他ユーザーを含め全10万件）の条件で計測した結果（2026-11-03）を下に示す。

| タグなしの件数 | 1ページ目（10件） | 件数取得（paginate） |
| --- | --- | --- |
| 3件（更新日時が最も古い） | 約0.5ms | 約0.2ms |
| 1% | 約1.0ms | 約0.4ms |
| 10% | 約1.6ms | 約2.8ms |
| 50% | 約0.7ms | 約14ms |
| 90% | 約0.3ms | 約24ms |

件数取得は、タグなしの行ごとに `articles` を主キーで引いて `deleted_at` を確認するため、タグなしが多いほど遅くなる。個人用のメモアプリとして許容範囲と判断した。改善が必要になったら、このテーブルに `deleted_at` も持たせる案がある（同条件で約4ms以下になることを確認済み。代わりに、ゴミ箱への移動・復元のたびに同期が必要になる）。

閲覧数順の並べ替えは相関サブクエリで行う。比較のために JOIN でも計測したが、一時テーブルが作られるため約3倍遅かった。
