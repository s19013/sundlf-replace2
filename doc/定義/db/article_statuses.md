# カラム

| カラム名   | ラベル   | 型                  | nullable | デフォルト値 | インデックス | 備考                                                    |
| ---------- | -------- | ------------------- | -------- | ------------ | ------------ | ------------------------------------------------------- |
| article_id | メモID   | bigint(20) UNSIGNED | false    |              | true         | 主キー、外部キー（`articles.id`）                       |
| count      | 閲覧数   | bigint(20) UNSIGNED | false    | 0            | false        | 閲覧数増加APIで加算される（`メモ閲覧数増加api.md`参照） |
| created_at | 作成日時 | timestamp           | true     | NULL         | false        |                                                         |

メモ（[`articles.md`](./articles.md)）のうち、ユーザーが直接変更しない閲覧数（`count`）を管理するテーブル。

# リレーション

## article_id

`articles.id` を参照する外部キー。1つのメモに対して1行だけ存在する（1対1）。

# 制約

## article_id

主キー制約。1つのメモに対して status の行が複数作られないようにする。

外部キー制約（`article_statuses_article_id_foreign`）。`ON DELETE CASCADE` のため、参照先のメモが削除されると、このテーブルの行も削除される。

# 備考

## 分離した理由

- `count` は閲覧のたびに加算され、書き込みが頻繁な値である。編集日時（`edited_at`）とも、検索の絞り込みとも関係しない。
- 本体と別にしておくと、閲覧数の加算で本体の行（`updated_at` を含む）を更新せずに済み、本体の行のロックとも競合しない。
- 関連 issue: #118、#122、#127、#134

## has_tags を本体へ戻した経緯

- #127 では、`has_tags` もこのテーブルで管理していた。当時は本体の `updated_at` が「編集日時」を兼ねていたため、タグ削除で `has_tags` が変わっても本体の更新日時を変えないようにする必要があったため。
- しかし、タグなし検索の絞り込みに使う列が2つのテーブルに分かれ、本体の複合インデックスだけで絞り込めなくなった（20,000件中タグなし3件で1ページ目約41ms）。
- #134 で、行の更新日時（`updated_at`）と編集日時（`edited_at`）を分けた。本体の行を更新しても並び順や排他制御に影響しなくなったため、`has_tags` を本体に戻した（[`articles.md`](./articles.md)参照）。

## 行の作成・削除

- メモ作成時に、同じトランザクション内でこのテーブルの行も作成する。
- 論理削除（ゴミ箱）中も行は残す。メモが物理削除されたときに CASCADE で削除される。

## 行が無い場合の扱い

行は作成時のイベントと移行で必ず作られる前提だが、イベントを通さずに作られたメモなどで欠けた場合は、既定値（`count = 0`）として扱う。閲覧数の加算は UPDATE だけなので、行が無いと反映されない（自動では補わない）。

## 閲覧数順の並べ替え

相関サブクエリで行う。比較のために JOIN でも計測したが、一時テーブルが作られるため約3倍遅かった。
